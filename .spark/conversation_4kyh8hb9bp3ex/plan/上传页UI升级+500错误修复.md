## 实现方案

### 一、修复 500 错误

**根因**：Kimi API key 硬编码且失效，上传文件时返回 `401 Invalid Authentication`。

**修复**：
1. 将 `KIMI_API_KEY` 从硬编码改为 `process.env.KIMI_API_KEY`，未配置时自动走 mock 模式
2. Mock fallback 逻辑：
   - 从 `MOCK_VIDEO_TAGS` 中随机选一个视频的分镜数据返回
   - 模拟 2~4 秒延迟，模拟真实分析过程
   - 返回的字段与真实 API 完全一致（shots + productModel + industry + quality 等）
3. 错误分类透传：401 →「API 密钥无效」；超时 →「分析超时」；网络错误 →「网络异常」
4. Controller 层捕获异常，返回结构化错误 `{ error: { code, message } }`，前端按类型展示

## 影响范围与风险

- 上传页是重写而非小改，需确保 dataloom 上传逻辑保持正确
- Mock fallback 只在 Kimi 不可用时触发，不影响真实 API 调用
- 任务列表使用本地 state 管理，刷新页面后丢失（原型阶段可接受）
- 批量上传时依次串行执行，避免并发导致的 API 限流问题

## 验收标准

1. 上传视频后不再返回 500 错误

3. 上传页顶部有 5 步流程进度条，当前步骤高亮
4. 两个上传卡片（成片素材/实拍素材），虚线框 + 上传图标
5. 上传状态 Tab（全部/待上传/上传中/已完成/上传失败）可切换筛选
6. 上传任务列表显示每个文件的进度和状态
7. 上传失败的任务有"重试"按钮
8. 支持批量选择、批量删除
9. 无 TS 报错，类型检查通过
10. 上传完成后素材库中能看到新素材，可打开详情查看分镜
